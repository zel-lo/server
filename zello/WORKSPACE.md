# 워크스페이스 실제 데이터 API

기본 워크스페이스 API는 기존 테이블을 사용합니다. 2026-11-08에 추가한 완료 기록·자동 초안 기능은 아래 설명의 Flyway V12 마이그레이션이 필요합니다.

모든 경로는 `/api/projects/{projectId}` 아래에 있고 활성 프로젝트 멤버십과 서버 세션을 요구합니다. 변경 요청에는 CSRF가 필요합니다. 응답에는 no-store를 적용합니다. 목록은 page=1부터 시작하고 페이지당 30개, hasNext로 다음 페이지를 안내합니다.

| 경로 | 동작 |
| --- | --- |
| GET /summary | 연결이 해제되지 않은 저장소의 비보관 이슈 집계, 내 미완료 작업, 개인 미확인 알림, 연결 저장소 수, 최근 1년 활동 일별 집계 |
| GET /activities | 프로젝트 활동 이력 |
| GET /notifications?unread=true | 로그인 사용자에게 온 프로젝트 알림 |
| PATCH /notifications/{id} | read boolean으로 읽음/읽지 않음, 수신자만 가능 |
| POST /notifications/read-all | 현재 프로젝트의 본인 알림 모두 읽음 |
| GET /patch-notes | 패치노트 목록 |
| GET /patch-notes/{id} | 패치노트 상세 |
| POST /patch-notes | title, summary, publish로 작성 |
| PATCH /patch-notes/{id} | title, summary, version, publish로 수정/공개 |
| GET /sync-runs | 최근 수집 상태·범위·처리 개수·실패 사유 |
| GET /repositories/{repositoryId}/operations | 현재 사용자의 GitHub 접근권한 재검증 후 Actions/Deployments 각각 최근 10개 조회 |

패치노트는 VIEWER를 제외한 프로젝트 멤버가 작성·편집하며 버전 충돌은 409입니다. 최초 공개는 활동 이력에 한 번 기록합니다. 읽음 처리는 수신자와 프로젝트 ID를 모두 검사합니다. 페이지나 프로젝트를 바꾸면 클라이언트는 이전 요청을 취소합니다.

빌드와 배포는 별개의 GitHub API를 사용하며 빌드 성공에서 배포 성공을 추론하지 않습니다. 각 조회의 실패를 별도로 반환하고 배포 상태를 조회할 수 없으면 unknown으로 표시합니다. 외부 CI가 GitHub Deployments에 기록하지 않은 배포는 조회할 수 없습니다. GitHub에 쓰는 작업이나 자동 배포는 하지 않습니다.

웹훅 자동 수집은 이번 범위에 포함하지 않습니다. 수동 이슈 수집은 기존 `/issues/sync`를 사용합니다. 활동 이력은 현재 저장된 배정·멤버 관리·패치노트 공개 기록이며 전체 GitHub 커밋 이력과 다릅니다.

## 완료 기록과 규칙 기반 패치노트 (2026-11-08)

Flyway **V12__record_work_changes.sql**로 `work_changes`를 추가합니다. V1~V11을 적용한 DB에도 순서대로 적용할 수 있으며 기존 자료는 삭제하지 않습니다.

- 대시보드 직접 완료, GitHub 이슈 수집에서 확인한 닫힘, PR 병합과 수집 후 연결 이슈 상태 계산이 같은 완료 기록 서비스를 사용합니다.
- 이슈가 연결돼 있으면 `issue:{id}`, 이슈 없는 병합 PR은 `pr:{id}`를 프로젝트 내 고유 키로 사용합니다. 반복 수집과 재시도는 같은 기록을 갱신합니다.
- 이슈 직접 완료 후 연결 PR이 머지되면 기존 기록의 상태와 병합 근거를 보완합니다. 나중에 이슈를 연결한 독립 PR 기록은 CONSOLIDATED로 표시하고 초안에서 중복 표시하지 않습니다.
- 완료 기록이 처음 생길 때 한국 시간 기준 이번 주의 자동 초안을 준비합니다. 같은 주에 새로 확인된 완료 기록을 같은 미공개 초안에 모으며, 공개 후 새 작업이 생기면 새 초안을 만듭니다.
- 다시 연 작업은 REOPENED, 보관한 작업은 ARCHIVED로 기존 기록을 갱신합니다. 작업 상태를 없애거나 병합·배포 성공으로 추정하지 않습니다.
- 패치노트의 사람이 작성한 제목·소개와 자동 수집한 항목을 분리합니다. 자동 수집은 편집한 소개를 덮어쓰지 않습니다. 공개 후에는 항목의 제목·설명도 보존하고 원본 상태 변경만 표시합니다.
- `POST /patch-notes/collect`로 기존 DB에 저장된 완료 작업을 모을 수 있습니다. writer 권한과 CSRF가 필요하며 GitHub 재수집은 수행하지 않습니다.
- PR 작성의 팀 요약은 선택 사항입니다. 비어 있으면 PR 본문, 본문도 없으면 제목을 사용합니다. 이 자동 문구는 GitHub 본문을 덮어쓰지 않습니다.

LLM과 외부 분석 호출은 없습니다. `RuleBasedChangeFormatter`는 기존 문구를 사용하고 설명은 최대 1,200자로 제한합니다. `feat:` 계열/`새 기능` 접두사는 FEATURE, `fix:` 계열/`오류 수정` 접두사는 FIX, 나머지는 IMPROVE입니다. 이는 내용의 의미를 추론하는 분류가 아닙니다. 나중에 분석기를 붙일 위치는 이 포매터이며, 상태 반영·중복 방지·원본 연결은 그대로 유지할 수 있습니다.

GitHub에서 직접 머지한 변경은 기존 PR 가져오기/수집 후 반영됩니다. 웹훅 자동 동기화는 아직 포함하지 않습니다. 머지 기록은 배포 완료를 의미하지 않습니다. 테스트는 H2 API 통합 검증과 MySQL DDL 매핑 검증이며, 이번 환경에서는 Docker 소켓 접근 제한으로 실제 MySQL V12 적용은 실행하지 못했습니다.


## 사람이 작성하는 패치노트 반영 제목

- V12 이후 **V13__work_change_titles.sql**도 적용합니다. `title_written`은 원래 작업 제목과 사람이 작성한 반영 제목을 구분합니다. 기존 완료 기록은 미작성 상태로 시작하며 공개된 기록의 문구는 유지됩니다.
- 보드에서 완료로 이동하거나 기존 작업 상세에서 완료할 때 `PATCH /issues/{id}`에 `patchNoteTitle`(공백 제외 1~255자)을 보냅니다. 원래 이슈 제목과 GitHub 제목은 변경하지 않습니다.
- GitHub에서 닫힌 이슈와 병합된 PR을 수집하면 `changes[].needsTitle=true`로 응답하며 클라이언트에서 **반영 사항 작성 필요**로 표시합니다. 원본 제목·본문은 확인용으로 유지하고 제목을 자동 작성 완료로 간주하지 않습니다.
- `PATCH /patch-notes/{id}/changes/{changeId}`에 `title`, 패치노트 `version`을 보내 반영 제목을 작성하거나 수정합니다. writer 권한과 CSRF가 필요하며 타 프로젝트 접근은 404, 버전 충돌과 공개 후 항목 수정은 409입니다.
- 사람이 작성한 반영 제목은 재수집으로 덮어쓰지 않습니다. 독립 PR이 작업과 연결되면 기존 반영 제목도 통합된 작업으로 이어집니다.
- 자동 초안의 완료·병합 항목 중 미작성 제목이 있으면 공개를 거절합니다(`CHANGE_TITLE_REQUIRED`). 저장은 가능하므로 원본을 확인하며 제목을 보완할 수 있습니다.
- GitHub 변경은 기존 수동 가져오기 이후 반영되며, 이번 변경에서 자동 웹훅이나 LLM 처리는 추가하지 않습니다.


## 주간 PM 대시보드

`GET /api/projects/{projectId}/dashboard?week=YYYY-MM-DD`는 활성 프로젝트 멤버에게 선택한 프로젝트 주차의 진행률, 상태별 개수, 확인 항목, 담당자별 현황, 최근 완료 5개를 반환합니다. 응답은 no-store이며 GitHub API 호출이나 상태 변경을 수행하지 않습니다.

- 프로젝트의 시간대와 주차 설정을 사용하고 완료 시각은 해당 주차 시작 이상, 다음 주 시작 미만으로 비교합니다.
- 진행률 분모는 이번 주와 이전 주에 계획한 진행·검토·할 일 및 이번 주 완료 작업입니다. 백로그, 미래 계획, 보관 작업, 연결 해제한 저장소와 오래된 완료 기록은 제외합니다. 현재 계획 기준이며 과거 계획의 스냅샷을 추정하지 않습니다.
- 전체 완료 수는 이번 주 완료 이슈와 이슈에 연결되지 않은 병합 PR의 합입니다. 연결된 PR과 이슈를 두 번 세지 않습니다. 최근 목록은 사람이 작성한 패치노트 반영 제목을 우선 사용하고 미작성 여부도 반환합니다.
- 확인 항목에는 담당자가 없는 주간 작업, 3일 이상 지난 검토 요청/열린 PR, 현재 수정 요청 상태인 PR이 포함됩니다. 초안은 제외합니다. 검토 요청 기록이 없으면 PR 생성 시각을 사용하고 'PR 열린 지'로 구분합니다. 수정 요청 날짜를 수집하지 못한 경우 날짜를 추정하지 않습니다. 오래된 상태를 작업이 막혔다고 단정하지 않습니다.
- 담당자별 진행 수는 주간 계획의 진행 중 이슈, 검토 수는 현재 열린 비초안 PR의 REQUESTED 리뷰 요청, 완료 수는 위의 중복 제거한 주간 완료 기록을 사용합니다. 현재 맡은 작업과 검토할 PR의 제목·상세 링크도 반환합니다.
- 화면은 프로젝트 전체를 보여주며 조회 제한으로 일부 작업만 집계하거나 오래된 데모 수치를 합산하지 않습니다.


대시보드의 `week`는 선택 사항이며 생략하면 현재 프로젝트 주차입니다. 기간이 있는 프로젝트는 시작일부터 7일 간격의 주차만 허용하고, 기간이 없으면 월요일을 주차 시작으로 사용합니다. 범위 밖·잘못된 주차는 400이며 마지막 주의 완료 집계는 프로젝트 종료일까지만 포함합니다. 응답의 `currentWeek`, `projectStartDate`, `projectEndDate`로 선택 범위와 이번 주 복귀 버튼을 구성합니다.

주차 선택은 과거 상태의 스냅샷을 만들지 않습니다. 선택한 주 완료 기록과 현재 미완료 작업을 같은 주간 보드 기준으로 집계합니다. 현재 열린 PR과 리뷰 요청 중 선택한 주 종료 전에 생성된 항목을 표시하며, UI에서 현재 상태 기준임을 안내합니다. 업무 담당 카드는 이름과 업무만 표시하고 오른쪽 패널에서 목록을 확인합니다.
